## Чек лист для ревью кода
### Архитектура и Дизайн
- Соответствует ли решение требованиям?
- Правильно ли выбраны паттерны?
- Нет ли "божественных" классов?\
<small>(Класс не превышает 300-500 строк? Метод — 30-50 строк?)</small>
- Слабая связанность (Low Coupling)?\
<small>Можно ли вынести часть логики в отдельный сервис/компонент?</small>
- Сильная связность внутри модуля (High Cohesion)?\
<small>(Все методы класса делают одно дело)</small>

### Безопасность (InfoSec) — (Критично!)
- Нет хардкода секретов/паролей/токенов
- SQL-инъекции: Используются ли PreparedStatement / параметризованные запросы (JPA @Param)?\
<small>(Нет конкатенации строк для SQL и nativeQuery)</small>
- XSS: Есть ли экранирование пользовательского ввода в шаблонах\
<small>(Thymeleaf th:text, а не th:utext)</small>
- Валидация входных данных: Проверяются ли @NotNull, @Size, @Min на DTO/контроллерах?

### Производительность (Performance)
- Можно ли что-нибудь закешировать
- Нет N+1 запросов в Hibernate/JPA: Проверить, не дергает ли цикл БД внутри цикла\
<small>(использовать @EntityGraph или join fetch)</small>
- Используются ли индексы?\
<small>(Если в запросе есть WHERE по неиндексированному полю — красный флаг</small>
- Работа с памятью:\
<small>Нет ли утечек через ThreadLocal (проверить вызов remove()).</small>
- Очереди и пулы:\
<small>Не блокируется ли общий ForkJoinPool (если используете parallelStream для I/O)?</small>

### Обработка ошибок (Error Handling)
- Все ли исключения обработаны?\
<small>(Нет catch (Exception e) { e.printStackTrace(); } или пустых catch-блоков)</small>
- Кастомные исключения:\
<small>Используются ли бизнес-исключения (вместо проброса RuntimeException)?</small>
- Стандартизация ошибок:\
<small>Возвращаются ли ошибки по RFC 7807 (ProblemDetail) в REST-контроллерах?</small>
- Логирование: Логируются ли ошибки с правильным уровнем\
<small>(log.error для фатальных, log.warn для ожидаемых)?</small>
- Не раскрываются ли внутренности системы в ответе клиенту?\
<small>(Проверить, что стектрейс не попадает в JSON)</small>

### Тесты
- Написаны ли unit-тесты для новой логики?
- Есть ли интеграционные тесты для эндпоинтов?
- Используются ли моки для внешних зависимостей, а не настоящие системы?

### Код-стайл и Читаемость
- Названия переменных/методов говорят сами за себя
- Убраны ли закомментированные куски кода?
- Есть ли JavaDoc для публичных методов и сложных кусков?
- Соблюдается ли форматирование?

### Java
- Нет ли возможных NPE, проверить Optional
- Не хранятся ли деньги во float или double
- Нет ли проблем в if/switch
- Нет ли проблем в try/catch

### Spring
- Как инжектированы bean-ы и как создаются объект
- Нет ли циклических зависимостей?\
<small>(Если есть, решены через @Lazy или рефакторинг)</small>
- @Transactional на месте:\
<small>Проверка, что транзакция не вызывается изнутри класса (self-invocation) и не висит на private методах</small>
- Конфигурации: Вынесены ли настройки в application.yml

## Как хранить секреты?
### Уровень 0: Что категорически нельзя делать
- Хардкодить в коде: `String password = "admin123";`.
- Класть в `application.properties` без шифрования
- Хранить в переменных окружения без ограничений: переменные окружения видны всем процессам, запущенным от того же пользователя, и могут попасть в логи

### Уровень 1: Встроенные механизмы Spring Boot
В Spring Boot можно использовать `Jasypt` и встроенный механизм `Property Encryption`\
Вы задаете мастер-пароль при запуске приложения, а в `application.yml` лежат зашифрованные значения
```yaml
# application.yml
secret:
  password: ENC(kjshdf87y3r4hjkasdhjfkjashdf) # Зашифрованное значение
```
Где хранить мастер-пароль?

### Уровень 2: HashiCorp Vault (Современный стандарт)
У приложения есть токен, с помощью которого оно авторизуется в хранилище и получает секреты динамически.\
Можно динамически перевыпускать пароли к БД\
Аудит: кто, когда и зачем запрашивал секрет

### Уровень 3: KeyStore (Хранилище для TLS и JWT)
Типы KeyStore в Java:
- JKS (Java KeyStore): Старый формат (Java 8 и старше), используется .jks.
- PKCS12: Современный стандарт, используется .p12 или .pfx. Более безопасный и кроссплатформенный.

Что внутри:
- Ключи (Private Key): Секретный ключ для расшифровки или подписи.
- Сертификаты (Public Key / Certificate): Публичный ключ + информация о владельце, подписанный CA.

```java
KeyStore keyStore = KeyStore.getInstance("PKCS12");
try (FileInputStream fis = new FileInputStream("keystore.p12")) {
    keyStore.load(fis, "password".toCharArray()); // Пароль от хранилища
}

// для получения приватного ключа
Key key = keyStore.getKey("my-alias", "key-password".toCharArray());
PrivateKey privateKey = (PrivateKey) key;

// для получения публичного ключа
java.security.cert.Certificate cert = keyStore.getCertificate("my-alias");
PublicKey publicKey = cert.getPublicKey();
```

## SPI и ServiceLoader
### Сравнение API и SPI
**API (Application Programming Interface):**\
Библиотека предоставляет готовые классы/методы. Вы вызываете их, чтобы получить результат.\
_Пример:_ Вы вызываете `restTemplate.getForObject()`.\
**SPI (Service Provider Interface):**\
Библиотека предоставляет абстрактный класс или интерфейс, а вы пишете свою реализацию, которую библиотека будет вызывать, когда ей это нужно.\
_Пример:_ Вы пишете свой драйвер для базы данных, а JDK вызывает его через DriverManager.

### Как происходит работа с SPI и ServiceLoader-ом
- Интерфейс/Абстрактный класс: Создатель фреймворка объявляет интерфейс `MyPlugin`.
- Конфигурация: Провайдер (разработчик) создает файл в своей сборке по пути `META-INF/services/com.example.MyPlugin`.
- Содержимое файла: Внутри файла пишется полное имя класса-реализации: `com.mycompany.MySuperPlugin`.
- Загрузка: Когда фреймворк запускается, он вызывает `ServiceLoader.load(MyPlugin.class)`.
- Автоматическое обнаружение: Java сама сканирует все JAR-файлы в classpath, находит файлы с правильным именем, загружает указанные классы и создает их экземпляры.

## gRAPHql и n+1
```json
query {
  authors {
    name
    books {
      title
    }
  }
}
```
Наивная реализация:\
- Запрос 1 (N=1): Чтобы получить список всех авторов, выполняется `SELECT * FROM authors` (1 запрос).
- Запросы (N): Для каждого автора (допустим, их 100) выполняется `SELECT * FROM books WHERE author_id = ?` (100 запросов).
- Итого: 1 + 100 = 101 запрос к БД. Вместо одного JOIN-запроса или двух запросов с IN мы делаем 101. База данных (и сеть) захлебываются.

Обработка через `DataLoader`:
- Сбор идентификаторов: Пока резолверы для каждого автора по очереди пытаются запросить книги, DataLoader не выполняет запрос сразу. Он просто запоминает ID автора (authorId) во внутренней очереди.
- Отложенный запуск: Как только все резолверы отработали (или через микро-тик), DataLoader запускает один пакетный запрос: SELECT * FROM books WHERE author_id IN (1, 2, 3, ..., 100).
- Сортировка: DataLoader получает список книг, группирует их по author_id и отдает каждому автору его список книг.
- Итог: 1 (запрос авторов) + 1 (пакетный запрос книг) = 2 запроса к БД. Проблема решена!
