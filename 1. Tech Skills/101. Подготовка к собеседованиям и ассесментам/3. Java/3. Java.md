Stream API поддерживает множество паралельных операций обработки данных и чем-то напоминает язык запросов БД. Не нужно  упрвлять многопоточностью самому

### Проблемы при parallel
#### Проблема №1
```java
List<Integer> numbers = IntStream.rangeClosed(1, 10000).boxed().collect(Collectors.toList());
List<Integer> result = new ArrayList<>(); // НЕ потокобезопасный!

numbers.parallelStream()
       .filter(x -> x % 2 == 0)
       .forEach(result::add); // ❌ ОПАСНО! add() не синхронизирован, будут коллизии и потеря элементов
```
Пофиксить можно так
```java
List<Integer> result = numbers.parallelStream()
                              .filter(x -> x % 2 == 0)
                              .collect(Collectors.toList()); // ✅ Безопасно!
```
или так
```java
List<Integer> result = new CopyOnWriteArrayList<>();
numbers.parallelStream().forEach(result::add); // ✅ Безопасно (но медленно)
```

#### Проблема №2
Если операции простые и мало элементов, то накладные расходы превышут выигрыш

#### Проблема №3
Все parallelStream() по умолчанию используют общий пул ForkJoinPool.commonPool(), который по умолчанию содержит Runtime.getRuntime().availableProcessors() - 1 потоков\
Проблема: Если вы запустите внутри parallelStream() тяжелую синхронную операцию (например, запрос в БД или HTTP-вызов), этот пул заблокируется. Все остальные parallelStream в приложении будут стоять в очереди, и приложение может зависнуть.

## ForkJoinFramework
Инфраструктура Fork/Join Framework улучшает многопоточное программирование двумя способами:
* упрощает создание и использование нескольких потоков
* автоматизирует использование нескольких процессоров (при использовании Fork/Join Framework приложениям позволяется автоматически масштабировать количество доступных процессоров)

`RecursieAction`, `RecursiveTask<V>`<br/>
ForkJoinPool управляет выполнением своих потоков, используя поток захвата задачи (work-stealing).
Каждый рабочий поток поддерживает очередь задач. Если очередь одного потока оказывается пустой, то она возьмет задачу от другого потока. Это способствует повышению производительности и помогает поддерживать баланс нагрузки.<br/>
Как правило Fork / Join Framework применяет стратегию "разделяй и властвуй"., лежащую в основе рекурсии.<br/>
Стратегия "разделяй и властвуй" подразумевает разделение адач на подзадачи, пока их размер не станет достаточно маленьким для последовательной обработки.<br/>
```java
class CrowdToRaidGroupsTask extends RecursiveTask<Integer> implements GroupToRaidDivider {...
    @Override
    protected Integer compute() {
        if (underRaidGroupMateLimit(crowd)) {
            ...
        } else {
            ...
            // Запуск подзадач ветвления
            firstPartTask.fork();
            secondPartTask.fork();

            // Ожидание заверения и получение результата
            Integer firstPartGroupsNumber = firstPartTask.join();
            Integer secondPartGroupsNumber = secondPartTask.join();
            return firstPartGroupsNumber + secondPartGroupsNumber;
        }
    }...
}
```

## ArrayList быстрее (в частности в переборе), чем LinkedList
`ArrayList` хранит данные в непрерывном куске памяти. `LinkedList` же выделяет память для каждого узла и связывает их ссылками

## Почему String сделали неизменяемым
Ради безопасности:
* можно передавать между потоками и не беспокоится, что будет изменена
* можно кэшировать хэш-код

String pool позволяет экономить память и не создавать новые объекты для каждой повторяющийся строки

## Альтернатива reflection
## MethodType
Представляет сигнатуру типов метода (возвращаемый тип и типы аргументов)

### MethodHandle
Дескриптор метода. Похож на Method в рефлексии, но современнее и удобнее.\
Для поиска используется контекст поиска, вызываемый статическим методом `MethodHandlers.lookup()`
```java
MethodHandler mh = null;
var mt = MethodType.methodType(String.class);
var lk = MethodHandlers.lookup();
try {
  mh = lk.findVirtual(getClass(), "toString", mt);
  mh.invokeExact(obj);
} catch(NoSuchMethodException | IllegalAccessException e) { ... }
```
### Преимущества по сравнению с рефлексией
Работает быстрее, имеется безопасность типов, полный доступ ко всем методам, разрешенным из текущего контекста

### LambdaMetafactory
был представлен в Java 8. Это дальнейшее развитие идеи динамического вызова.<br/>
позволяет нам генерировать экземпляр функционального интерфейса во время выполнения, который содержит ссылку на метод, разрешенный MethodHandle
```java
private BiConsumer createVoidHandlerLambda(Object bean, Method method) throws Throwable {
        MethodHandles.Lookup caller = MethodHandles.lookup();
        CallSite site = LambdaMetafactory.metafactory(caller,
                "accept",
                MethodType.methodType(BiConsumer.class),
                MethodType.methodType(void.class, Object.class, Object.class),
                caller.findVirtual(bean.getClass(), method.getName(),
                        MethodType.methodType(void.class, method.getParameterTypes()[0])),
                MethodType.methodType(void.class, bean.getClass(), method.getParameterTypes()[0]));
        MethodHandle factory = site.getTarget();
        BiConsumer listenerMethod = (BiConsumer) factory.invoke();
        return listenerMethod;
    }
```

### VarHandle
это "младший брат" `MethodHandle`, созданный специально для безопасной и быстрой работы с полями (включая volatile, CAS-операции).\
Раньше это делали через Unsafe (опасно), а теперь через VarHandle (безопасно).\
Он тоже использует `MethodHandles.lookup`, но для доступа к полям, а не к методам.
Можно получить через `MethodHandles`<br/>
Можно делать `get`, `set`, `getAndAdd`

## Java Microbenchmark Harness (JMH)
официальный инструмент от OpenJDK для написания корректных бенчмарков. Он решает проблемы JIT-компиляции, дед-код элиминации и нестабильности результатов, которые возникают при наивных замерах через System.currentTimeMillis().\
JMH автоматически разогревает код (Warmup), запускает тесты в отдельных JVM-процессах (Forks), собирает статистику и позволяет измерять в разных режимах.

- `SampleTime` - для обнаружения выбросов
- `SingleShotTime`	Выполняет метод один раз (без прогрева)

## Управление памятью
### Стек (Stack)
Стековая память отвечает за хранение ссылок на объекты кучи и за хранение примитивов, которые содержат само значение, а не ссылку на объект из кучи.\
Кроме того, переменные в стеке имеют областью видимости. Используются только объекты из активной области.\
Когда метод завершается и возвращается, верхняя часть стека выталкивается, и активная область видимости изменяется.\
стековая память в Java выделяется для каждого потока. Следовательно, каждый раз, когда поток создается и запускается, он имеет свою собственную стековую память и не может получить доступ к стековой памяти другого потока.

### Куча (Heap)
Эта часть памяти хранит в памяти фактические объекты, на которые ссылаются переменные из стека.\
Куча общая независимо от того, сколько потоков выполняется.

### Ключевое слово new
несет ответственность за обеспечение того, достаточно ли свободного места на куче, создавая объект нужного типа в памяти и обращаясь к нему через «builder» ссылки, которая попадает в стек.

### Сборщики мусора
#### G1
Делит кучу не только на поколения, но и на регионы, чтобы обеспечить примерно одинаковое и предсказуемое время выполнения сборки мусора.\
До этого, если сборка начиналась, то шла до конца.\
Имеет параметры:

- `-XX:MaxGCPauseMillis=50` - по возможности не дольше
- `-XX:GCPauseIntervalMillis=50` - по возможности такой интервал между сборками

#### ParallelGC
Самый эффективный, но нельзя устанавливать целевую продолжительность

#### Некоторые параметры

- `-Xms123m` - начальный размер кучи. Дальше саморасширяется
- `-Xmx123m` - максимальный размер кучи
- `-Xmn123m` - размер молодого поколения
- `-XX:+DisableExplicitGC` - блокирует вызовы `System.gc`

## Многоверсионные Jar
Multi-Release JAR (MR-JAR) появился в Java 9
```shell
jar-файл.jar
├── META-INF/
│   └── MANIFEST.MF       # <-- Обязательно содержит запись: Multi-Release: true
├── com/                  # <-- Базовая версия для Java 8 и старше
│   └── example/
│       └── MyClass.class
└── META-INF/
    └── versions/
        ├── 9/            # <-- Версия для Java 9 и новее
        │   └── com/
        │       └── example/
        │           └── MyClass.class
        └── 11/           # <-- Версия для Java 11 и новее (опционально)
            └── com/
                └── example/
                    └── MyClass.class
```
В MANIFEST.MF обязательно должна быть строка `Multi-Release: true`, чтобы JVM знала, что это особый JAR\
Компиляция классов под нужную версию `javac --release 11 ...`\
Сборка под нужную версию `jar --create --file my-multi-release.jar -C out/base . --release 9 -C out/java9 .`
